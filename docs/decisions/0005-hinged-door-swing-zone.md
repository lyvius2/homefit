# ADR 0005 — 여닫이문 열림 영역을 충돌 판정에 넣는다

- 날짜: 2026-11-01
- 상태: 승인 (소유자 요청, 미닫이문은 범위에서 제외)
- 관련: 설계서 Section 2.3(openings.swing), 3(문 열림 영역), 5(S-03, S-06), 7(M8), 8(열린 결정 2)

## 배경

설계서 v0.1은 문·창 개구부를 데이터 스키마로만 두고 에디터·3D·판정 어디에도 쓰지 않았다(열린 결정 2). 소유자가 실제로 배치를 해 보니 문이 열리고 닫히는 영역에 집기를 놓아도 아무 경고가 없어 "들어가는지"를 믿을 수 없었다. 미닫이문도 검토했으나 소유자가 여닫이만 구현하기로 정했다.

## 결정

1. **스키마**: `opening`에 선택 필드 `swing { hinge: "a" | "b", side: "left" | "right" }`를 둔다. 문 전용이며 없으면 열림 영역을 만들지 않는다. 기존 저장 데이터(시드 포함)와 호환되도록 필수로 만들지 않았다. 창에 `swing`이 있으면 `Plans::Validate`가 거부한다. 같은 검증에 `offset + width ≤ 벽 길이`와 같은 벽 개구부 겹침 금지를 추가했다(이전에는 참조 무결성만 검사).
2. **기하**: 경첩점을 벽면 위(중심선 + n·t/2)에 두고, 반지름 = 문 폭의 90° 부채꼴을 **8등분한 볼록 10각형**으로 근사한다. 기존 SAT가 `corners`/`axes`만 쓰므로 다각형용 `Polygon`(축 = 변 법선)을 추가해 그대로 재사용했다. 사각형 근사(문 폭 × 문 폭)는 구현이 더 단순하지만 모서리 21%가 거짓 양성이라 택하지 않았다. 양쪽 구현의 기대값은 Python 독립 구현으로 만들어 `docs/geometry-fixtures.json`에 넣었다.
3. **판정 등급**: 열림 영역 침범은 벽 침범과 같은 급으로 **저장을 막는다**(R-08 확장, 사유 `door:<opening_id>`, 순서는 wall 뒤·out_of_bounds 앞). 경고만 주는 안은 "맞는지 확인"이라는 앱의 목적과 맞지 않아 택하지 않았다. 판정은 평면 기준이라 문 높이보다 높은 z_mm 의 선반도 침범으로 본다 — 보류 항목.
4. **도면 에디터**: "문 놓기" 도구. 벽 300 mm 이내 클릭 → 클릭 지점을 중심으로 폭 800 mm 기본, 10 mm 스냅, 벽 안으로 클램프. 열리는 면은 **클릭한 쪽**, 경첩은 `a` 쪽이며 사이드바에서 둘 다 반전한다. 캔버스는 벽 레이어에서 개구부 구간을 `destination-out`으로 지워 틈을 내고, 열린 문짝과 열림 부채꼴을 판정과 같은 `doorZone()` 꼭짓점으로 그린다(그림과 판정이 어긋날 수 없다).
5. **배치 에디터**: 벽 메시를 CSG 대신 **조각 박스**로 나눈다(개구부 사이 전고, 개구부 위 상인방, 창 아래 조각). 열림 영역은 바닥의 반투명 `shapeGeometry` + 외곽선, 문짝은 90° 열린 얇은 박스.

## 영향

- `app/schemas/plan_v1.json`, `Plans::Validate`, `Geometry::{Polygon,DoorZone,Collisions}`, `geometry.ts`/`collisions.ts`, `docs/geometry-fixtures.json`, `PlanEditor/*`, `LayoutEditor/{Scene,wallPieces,Panels,store}`, `House#openings`, `Placements::Validate`, 시드.
- 시스템 테스트는 핵심 흐름 3개 규칙대로 추가하지 않았다. 두 에디터는 임시 시스템 테스트로 브라우저 확인 후 삭제했다.
